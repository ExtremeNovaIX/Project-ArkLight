# 项目愿景

ArcLight-chat 的游戏链路不是为了写一套规则替 agent 玩游戏。它的核心目标是探索 LLM 在开放状态、连续反馈、工具执行和失败重规划中的泛化推理上限。游戏是当前最适合压测这件事的场景，因为它同时要求局面理解、资源权衡、长期目标、短期动作、异常恢复，以及从自然语言到工具调用的转换。

## 核心原则

- LLM 是游戏步骤的主要生成者。系统应尽量让模型基于最新上下文决定下一步，而不是由后端算法枚举、搜索、排序或合成具体操作序列。
- 后端职责是提供上下文、执行模型明确提出的动作、记录过程、反馈失败并维护运行边界。后端不应演化成策略引擎或代打器。
- 规则、parser、adapter 和 MCP 只服务于把 LLM 的意图可靠落到工具调用上。它们可以做格式转换、索引映射、状态读取、错误反馈和必要的边界处理，但不应该替模型选择战术步骤。
- 当模型算错、说多了或失败时，优先改进上下文、控制协议、反馈和重规划机制，让模型自己修正。不要默认用算法接管决策。
- 项目接受 LLM 在探索期犯错。错误需要可追踪、可复盘、可反馈，而不是被后端静默修掉。

## 非目标

- 不以构建最强 STS2 自动玩家为主要目标。
- 不以穷举卡牌组合、规则搜索、收益函数、后端算费或算法代打作为主路线。
- 不把游戏步骤生成下沉到规则系统中，除非这是为了做明确的对照实验，并且不会进入默认链路。

## 对工程设计的要求

- 给 agent 展示它需要自己判断的信息，包括当前能量、敌人意图、格挡缺口、手牌、行动约束和执行失败原因。
- 执行链路忠实反馈模型动作的结果，包括成功、失败、状态变化、中断和异常。
- trace 记录模型可见上下文、输出、动作和反馈，方便分析 LLM 推理执行边界。
- 任何看起来能提升胜率但会替模型生成动作的规则，都应先被视为和项目愿景冲突。
